# Payload Doctor rule catalogue

Generated by `pdoc rules --markdown`. Each rule explains why the problem matters, its likely cause and the fix, so this file doubles as a support knowledge base.

## AS2

### AS2-001: Certificate has expired

- **Severity:** error
- **Why it matters:** AS2 messages signed or encrypted with an expired certificate are rejected, and MDNs stop arriving.
- **Likely cause:** Certificate renewal was not exchanged with the trading partner before the expiry date.
- **Fix:** Generate or obtain a new certificate, exchange it with the partner, update both AS2 profiles, then resend failed messages.

### AS2-002: Certificate expires within 30 days

- **Severity:** warning
- **Why it matters:** Partners often need weeks to schedule a certificate change; an expiry mid-week stops all traffic.
- **Likely cause:** Renewal not yet planned.
- **Fix:** Plan the certificate exchange now and agree a switch-over date with the partner.

### AS2-003: Weak key size

- **Severity:** warning
- **Why it matters:** RSA keys under 2048 bits are rejected by many current AS2 gateways.
- **Likely cause:** Old certificate generated with a 1024-bit key.
- **Fix:** Issue a new certificate with an RSA key of at least 2048 bits.

### AS2-004: Certificate signed with SHA-1

- **Severity:** warning
- **Why it matters:** SHA-1 is deprecated; some partners refuse it.
- **Likely cause:** Legacy certificate authority or old tooling.
- **Fix:** Reissue the certificate with SHA-256.

### AS2-005: Self-signed certificate

- **Severity:** info
- **Why it matters:** Common for AS2, but the partner must install this exact certificate; a renewal needs a new exchange.
- **Likely cause:** Certificate generated locally rather than by a certificate authority.
- **Fix:** No action needed if the partner has the certificate installed; track its expiry.

### AS2-006: Certificate not yet valid

- **Severity:** error
- **Why it matters:** Messages are rejected until the start date, often because of a time zone or clock issue.
- **Likely cause:** Certificate installed before its validity start, or the server clock is wrong.
- **Fix:** Check the server clock and the certificate's notBefore date.

### AS2-007: MDN reports the message failed

- **Severity:** error
- **Why it matters:** The partner received the message but did not process it; from their side it does not exist.
- **Likely cause:** Decryption or signature failure (certificate mismatch), or the payload failed their checks.
- **Fix:** Read the disposition modifier: 'decryption-failed' or 'authentication-failed' means a certificate mismatch; fix and resend.

### AS2-008: MDN could not be read

- **Severity:** warning
- **Why it matters:** Without a readable receipt there is no proof of delivery.
- **Likely cause:** Partner sent an unsigned or non-standard MDN, or the file is not an MDN.
- **Fix:** Ask the partner to check their MDN settings (signed, synchronous or asynchronous as agreed).

## CSV

### CSV-001: Header row missing or has duplicate/blank column names

- **Severity:** error
- **Why it matters:** Receivers map columns by header name; without a clean header every value lands in the wrong field.
- **Likely cause:** File exported without headers, or a spreadsheet with merged/blank header cells.
- **Fix:** Export with one header row and unique, non-blank column names.

### CSV-002: Row has the wrong number of columns

- **Severity:** error
- **Why it matters:** Shifted columns put values into the wrong fields (a quantity read as a date, for example).
- **Likely cause:** Unquoted comma inside a value (e.g. a company name), or a truncated line.
- **Fix:** Quote values that contain the delimiter, or remove the stray delimiter, and resend.

### CSV-003: Required value is empty

- **Severity:** error
- **Why it matters:** Identifier, quantity, lot and date columns are needed to process each row.
- **Likely cause:** Blank cells in the source spreadsheet or a mapping gap.
- **Fix:** Fill the empty cells in the source data and re-export.

### CSV-004: Date is not in ISO format (YYYY-MM-DD)

- **Severity:** error
- **Why it matters:** Dates like 03/04/2026 are ambiguous (3 April or 4 March?) and break sorting and comparisons.
- **Likely cause:** Spreadsheet locale formatting applied on export.
- **Fix:** Format date columns as YYYY-MM-DD before exporting.

### CSV-005: GTIN check digit is wrong

- **Severity:** error
- **Why it matters:** A GTIN with a wrong check digit matches no product, so the row is rejected.
- **Likely cause:** Typo, a leading zero removed by Excel, or a digit transposed.
- **Fix:** Correct the GTIN (keep leading zeros by formatting the column as text) and resend.

### CSV-006: Quantity is not a positive number

- **Severity:** error
- **Why it matters:** Quantities must be numeric for stock and order updates.
- **Likely cause:** Text such as '10 boxes', a decimal comma, or a negative adjustment in the wrong file.
- **Fix:** Send plain numbers (e.g. 10 or 10.5) in quantity columns.

### CSV-007: Delimiter is not a comma

- **Severity:** warning
- **Why it matters:** The receiver may expect commas and read the whole row as one column.
- **Likely cause:** Spreadsheet saved with a European locale (semicolon) or as tab-separated.
- **Fix:** Confirm the agreed delimiter with the partner, or re-export as comma-separated.

### CSV-008: Duplicate rows

- **Severity:** warning
- **Why it matters:** Duplicate lines double-count stock or create duplicate orders.
- **Likely cause:** Export run twice into the same file, or a copy-paste error.
- **Fix:** Remove duplicate lines, or confirm with the partner that they are intended.

## EDIFACT

### EDI-001: UNB/UNZ interchange references do not match

- **Severity:** error
- **Why it matters:** The interchange control reference is how duplicates and losses are detected; mismatches are rejected.
- **Likely cause:** Envelope built by a custom script or two interchanges merged.
- **Fix:** Make UNZ02 equal UNB05 and resend.

### EDI-002: UNZ message count is wrong

- **Severity:** error
- **Why it matters:** UNZ01 must equal the number of UNH messages (or UNG groups) in the interchange.
- **Likely cause:** Messages added or removed without updating the trailer, or a truncated transfer.
- **Fix:** Recount UNH segments and correct UNZ01.

### EDI-003: UNH/UNT message references do not match

- **Severity:** error
- **Why it matters:** The receiver cannot pair the message header with its trailer.
- **Likely cause:** Template that hard-codes one of the two references.
- **Fix:** Make UNT02 equal UNH01.

### EDI-004: UNT segment count is wrong

- **Severity:** error
- **Why it matters:** UNT01 counts every segment from UNH to UNT inclusive; a mismatch means segments were lost or added.
- **Likely cause:** Map changed without recalculating the count.
- **Fix:** Recalculate UNT01 (UNH..UNT inclusive).

### EDI-005: Envelope segment missing

- **Severity:** error
- **Why it matters:** Without UNZ/UNT the receiver cannot confirm the interchange arrived complete.
- **Likely cause:** Truncated transfer or an export that stopped early.
- **Fix:** Compare file sizes with the sender and request a full resend.

### EDI-006: Message type not covered by Payload Doctor

- **Severity:** warning
- **Why it matters:** Only envelope checks were run for this message.
- **Likely cause:** Message type other than ORDERS, DESADV or CONTRL.
- **Fix:** Validate the business content manually or add rules for this message type.

### EDI-007: ORDERS has no delivery party (NAD+DP or NAD+ST)

- **Severity:** error
- **Why it matters:** Without a delivery party the order cannot be routed to the right site.
- **Likely cause:** Address block skipped in the partner's map.
- **Fix:** Add NAD+DP (or NAD+ST) with a GLN or address and resend.

### EDI-008: Message has no line items (LIN)

- **Severity:** error
- **Why it matters:** An order or despatch advice without lines carries no products.
- **Likely cause:** Lines filtered out by the export.
- **Fix:** Re-export including LIN/QTY segment groups.

### EDI-009: DESADV has no despatch date (DTM+11)

- **Severity:** warning
- **Why it matters:** Receiving teams plan the dock schedule from the despatch date.
- **Likely cause:** Date not set when the DESADV was generated.
- **Fix:** Add DTM+11 with the actual despatch date/time.

### EDI-010: QTY value is not a positive number

- **Severity:** error
- **Why it matters:** Quantities must be numeric for allocation and receiving.
- **Likely cause:** Decimal mark mismatch (comma vs point) or text in a numeric field.
- **Fix:** Send QTY as a plain number using the decimal mark declared in UNA.

### EDI-011: CONTRL reports the interchange or a message was rejected

- **Severity:** error
- **Why it matters:** The partner's system refused the original interchange; it was not processed.
- **Likely cause:** Syntax error in the original file (see UCS/UCD segments for the exact place).
- **Fix:** Read UCS/UCD to locate the error, fix the original interchange and resend.

### EDI-012: Segment outside a message

- **Severity:** error
- **Why it matters:** Business segments must sit between UNH and UNT.
- **Likely cause:** Missing UNH, or two interchanges merged.
- **Fix:** Check the segment order around the reported position.

## EPCIS

### EPC-001: Not an EPCIS 1.2 document

- **Severity:** error
- **Why it matters:** The receiver expects an EPCISDocument in the urn:epcglobal:epcis:xsd:1 namespace.
- **Likely cause:** Wrong namespace (e.g. EPCIS 2.0), wrong root element, or a different XML message sent.
- **Fix:** Confirm the agreed EPCIS version with the partner and send an EPCISDocument with the 1.2 namespace.

### EPC-002: Event is missing a required field

- **Severity:** error
- **Why it matters:** eventTime, eventTimeZoneOffset and action are mandatory; events without them are rejected.
- **Likely cause:** Mapping gap in the serialization or warehouse system.
- **Fix:** Populate the missing field for every event in the export.

### EPC-003: Malformed EPC identifier

- **Severity:** error
- **Why it matters:** A malformed SGTIN or SSCC cannot be matched to a product or pallet, so verification fails.
- **Likely cause:** Wrong GS1 company prefix length, extra digits, or a serial number longer than 20 characters.
- **Fix:** Rebuild the EPC from the correct GS1 company prefix and item reference (13 digits together for SGTIN).

### EPC-004: Duplicate serial number

- **Severity:** error
- **Why it matters:** Each serialized unit must be unique; duplicates are a red flag for counterfeit or data errors and block receiving.
- **Likely cause:** Serial number re-used by the serialization system, or the same event sent twice in one document.
- **Fix:** Investigate the serial range with the packaging line; decommission the duplicate and send corrected data.

### EPC-005: Aggregated unit was never commissioned

- **Severity:** error
- **Why it matters:** A case or pallet claims to contain a unit that has no commissioning event, so its data cannot be verified.
- **Likely cause:** Units re-packed after commissioning, or commissioning events dropped from the file.
- **Fix:** Include the commissioning event for every child EPC, or correct the aggregation (childEPCs).

### EPC-006: Commissioning event without lot number or expiry date

- **Severity:** error
- **Why it matters:** Lot and expiry are required product data for pharma traceability (for example US DSCSA).
- **Likely cause:** ILMD block missing or mapped to the wrong namespace.
- **Fix:** Add <extension><ilmd> with cbvmda:lotNumber and cbvmda:itemExpirationDate to each commissioning event.

### EPC-007: Invalid expiry date format

- **Severity:** error
- **Why it matters:** Expiry must be an ISO date (YYYY-MM-DD); other formats cannot be compared or displayed reliably.
- **Likely cause:** Date sent as DD/MM/YYYY or YYMMDD from a label system.
- **Fix:** Send cbvmda:itemExpirationDate as YYYY-MM-DD.

### EPC-008: Product is already expired

- **Severity:** warning
- **Why it matters:** Expired product should not be shipped; the receiver will quarantine it.
- **Likely cause:** Wrong lot selected at picking, or an incorrect expiry date in master data.
- **Fix:** Confirm the lot and expiry with the warehouse before the goods arrive.

### EPC-009: Shipping event has no source or destination owning party

- **Severity:** error
- **Why it matters:** Pharma traceability data must name who shipped and who received the goods.
- **Likely cause:** sourceList/destinationList not mapped, or a different source/destination type used.
- **Fix:** Add sourceList and destinationList entries of type urn:epcglobal:cbv:sdt:owning_party.

### EPC-010: Malformed eventTimeZoneOffset

- **Severity:** error
- **Why it matters:** Without a valid offset the event time cannot be placed correctly on the timeline.
- **Likely cause:** Offset sent as 'IST', '+0530' or '5:30' instead of '+05:30'.
- **Fix:** Send the offset as +HH:MM or -HH:MM, for example +05:30.

### EPC-011: Event time is in the future

- **Severity:** warning
- **Why it matters:** Events dated in the future usually mean a time zone mistake and confuse sequence checks.
- **Likely cause:** Local time sent with a UTC 'Z' suffix, or the server clock is wrong.
- **Fix:** Check the sender's clock and that eventTime and eventTimeZoneOffset describe the same instant.

### EPC-012: Document contains no events

- **Severity:** error
- **Why it matters:** An EPCIS document without events carries no traceability data.
- **Likely cause:** Export ran before the events were captured, or the EventList was filtered out.
- **Fix:** Re-export after the events are captured.

## ANY

### GEN-001: Byte-order mark (BOM) at start of file

- **Severity:** warning
- **Why it matters:** Many partner parsers treat the 3 invisible BOM bytes as data, so the first segment or tag is not recognised.
- **Likely cause:** File was saved as 'UTF-8 with BOM', usually by Excel, Notepad or a .NET export.
- **Fix:** Re-save as UTF-8 without BOM, or strip the first 3 bytes (sed -i '1s/^\xEF\xBB\xBF//' file).

### GEN-002: Unrecognised file format

- **Severity:** error
- **Why it matters:** The receiver cannot route a file it cannot identify, so it is usually parked or rejected silently.
- **Likely cause:** Wrong file sent (e.g. a PDF or a report), a truncated transfer, or an unusual envelope.
- **Fix:** Open the file and confirm what it is; ask the partner to resend the intended X12/EDIFACT/XML/CSV payload.

### GEN-003: File is empty

- **Severity:** error
- **Why it matters:** There is nothing to process; downstream systems may report the transaction as received but blank.
- **Likely cause:** Transfer started before the source file was fully written, or the export job produced no data.
- **Fix:** Check the partner's export job and file size on the SFTP server; ask for a resend after the write completes.

### GEN-004: File is not valid UTF-8 text

- **Severity:** error
- **Why it matters:** Characters such as accented names or symbols become garbage, and strict parsers stop at the first bad byte.
- **Likely cause:** File exported in a legacy encoding (Windows-1252, ISO-8859-1) or corrupted in transfer (FTP ASCII mode).
- **Fix:** Ask the partner to export as UTF-8, or convert with: iconv -f WINDOWS-1252 -t UTF-8 in > out.

## X12

### X12-001: ISA header malformed

- **Severity:** error
- **Why it matters:** The receiver reads the delimiters from fixed positions in ISA; if ISA is wrong nothing else can be parsed.
- **Likely cause:** ISA fields not padded to their fixed widths, or the file was edited by hand.
- **Fix:** Regenerate the interchange from the EDI translator; ISA must be exactly 106 characters.

### X12-002: ISA/IEA control numbers do not match

- **Severity:** error
- **Why it matters:** Translators use the control number to detect lost or duplicate interchanges, and reject mismatches.
- **Likely cause:** Envelope built by a custom script, or two interchanges concatenated.
- **Fix:** Make IEA02 equal ISA13 and resend.

### X12-003: IEA group count is wrong

- **Severity:** error
- **Why it matters:** IEA01 must equal the number of GS groups; a mismatch suggests the file was truncated or merged.
- **Likely cause:** Partial transfer, or groups added without updating the trailer.
- **Fix:** Recount GS/GE groups, fix IEA01 and resend; check the transfer log for a cut-off upload.

### X12-004: GS/GE control numbers do not match

- **Severity:** error
- **Why it matters:** The functional group cannot be acknowledged (997) when its header and trailer disagree.
- **Likely cause:** Envelope generation bug in the sender's translator.
- **Fix:** Make GE02 equal GS06 and resend.

### X12-005: GE transaction count is wrong

- **Severity:** error
- **Why it matters:** GE01 must equal the number of ST/SE sets in the group; otherwise the group is rejected.
- **Likely cause:** Transaction sets added or removed without updating GE01.
- **Fix:** Recount the ST segments in the group and correct GE01.

### X12-006: ST/SE control numbers do not match

- **Severity:** error
- **Why it matters:** The transaction set cannot be matched to its trailer, so the whole set is rejected.
- **Likely cause:** Template or mapping bug that hard-codes one of the two numbers.
- **Fix:** Make SE02 equal ST02.

### X12-007: SE segment count is wrong

- **Severity:** error
- **Why it matters:** SE01 counts every segment from ST to SE inclusive; receivers use it to detect missing segments.
- **Likely cause:** Segments added or dropped by the map without recalculating SE01.
- **Fix:** Recalculate SE01 (count ST..SE inclusive) in the map.

### X12-008: Transaction set not covered by Payload Doctor

- **Severity:** warning
- **Why it matters:** Only envelope checks were run; business rules for this transaction type were skipped.
- **Likely cause:** The interchange contains a transaction set other than 850, 856 or 997.
- **Fix:** Validate the business content manually or add rules for this transaction set.

### X12-009: Line breaks inside segments (wrapped file)

- **Severity:** warning
- **Why it matters:** Many translators treat a line break as data, so elements split across lines are read wrongly or the ISA header is rejected.
- **Likely cause:** File wrapped at a fixed width (often 80 characters) by a mainframe, mail gateway or FTP ASCII-mode transfer.
- **Fix:** Unwrap the file (tr -d '\r\n' < in > out) and ask the partner to send it unwrapped in binary mode.

### X12-010: Envelope segment missing

- **Severity:** error
- **Why it matters:** Without the trailer segments the receiver cannot tell whether the file arrived complete.
- **Likely cause:** Truncated transfer or an export that stopped mid-file.
- **Fix:** Compare file size with the sender's copy; ask for a full resend.

### X12-011: Segment outside a transaction set

- **Severity:** error
- **Why it matters:** Business segments must sit between ST and SE; anything else is ignored or rejected.
- **Likely cause:** Two interchanges merged, or a missing ST segment.
- **Fix:** Check the segment order around the reported position and regenerate the file.

### X12-012: Interchange is flagged as TEST (ISA15 = T)

- **Severity:** warning
- **Why it matters:** Production systems usually discard test interchanges, so the partner thinks it was sent but nothing is processed.
- **Likely cause:** Partner forgot to switch the trading-partner profile from test to production.
- **Fix:** Ask the partner to set ISA15 to P for production traffic and resend.

### X12-014: 850 has no ship-to party (N1*ST)

- **Severity:** error
- **Why it matters:** Without a ship-to party the receiver cannot route the order to a warehouse or customer site.
- **Likely cause:** The partner's ERP mapping skipped the address block, or the location is missing in master data.
- **Fix:** Add an N1*ST segment (with N3/N4 address or an ID in N103/N104) and resend; ask partner to check the map.

### X12-015: 850 BEG segment missing or PO number empty

- **Severity:** error
- **Why it matters:** The PO number is the key every later document (855, 856, 810) refers to.
- **Likely cause:** Order created without a PO number, or BEG mapped to the wrong field.
- **Fix:** Populate BEG03 with the purchase order number.

### X12-016: 850 has no line items (PO1)

- **Severity:** error
- **Why it matters:** An order without lines cannot be fulfilled.
- **Likely cause:** Lines filtered out by the export, or an order header sent on its own.
- **Fix:** Check the source order in the ERP and re-export including lines.

### X12-017: CTT line count does not match PO1 lines

- **Severity:** warning
- **Why it matters:** Receivers use CTT01 as a checksum; a mismatch suggests lost lines.
- **Likely cause:** Lines removed after the count was calculated.
- **Fix:** Recalculate CTT01 as the number of PO1 segments.

### X12-018: PO1 quantity is not a positive number

- **Severity:** error
- **Why it matters:** An order line with zero, negative or non-numeric quantity cannot be allocated.
- **Likely cause:** Unit-of-measure conversion bug, or a text value in a numeric field.
- **Fix:** Fix PO102 in the source order and resend.

### X12-019: Invalid date (expected CCYYMMDD)

- **Severity:** error
- **Why it matters:** Dates that do not parse break scheduling and ageing reports downstream.
- **Likely cause:** Date sent as YYMMDD, DD-MM-YYYY or with separators.
- **Fix:** Send dates as 8 digits, for example 20261124.

### X12-020: 856 BSN missing or shipment ID empty

- **Severity:** error
- **Why it matters:** The shipment ID links the ASN to the physical delivery at receiving.
- **Likely cause:** Shipment created without an ID in the warehouse system.
- **Fix:** Populate BSN02 with the shipment identifier.

### X12-021: 856 HL hierarchy broken

- **Severity:** error
- **Why it matters:** Each HL points to its parent; a broken link means items cannot be placed in their packs or shipment.
- **Likely cause:** HL parent IDs (HL02) generated out of order or after lines were removed.
- **Fix:** Regenerate the HL loop so every HL02 refers to an earlier HL01.

### X12-022: 856 has no item-level HL (HL03 = I)

- **Severity:** error
- **Why it matters:** The receiver cannot see what products are in the shipment.
- **Likely cause:** Only shipment/order levels were mapped.
- **Fix:** Add item-level HL loops with LIN/SN1 for each product.

### X12-023: 856 has no ship date (DTM*011)

- **Severity:** warning
- **Why it matters:** Receiving teams plan dock schedules from the ship date.
- **Likely cause:** Date not available at the time the ASN was generated.
- **Fix:** Add DTM*011 with the actual ship date.

### X12-025: 997 reports a rejected transaction or group

- **Severity:** error
- **Why it matters:** The partner's system refused the original document, so it was NOT processed on their side.
- **Likely cause:** The original file failed the partner's validation (see AK3/AK4 for the exact segment).
- **Fix:** Read the AK3/AK4 segments to find the failing segment, fix the original document and resend it.

### X12-026: 997 reports accepted with errors

- **Severity:** warning
- **Why it matters:** The document was processed, but some data was ignored.
- **Likely cause:** Optional elements the partner does not support or invalid code values.
- **Fix:** Review the AK3/AK4 details with the partner and correct the map.

## XML

### XML-001: XML is not well-formed

- **Severity:** error
- **Why it matters:** A non-well-formed document cannot be parsed at all, so every event in it is lost.
- **Likely cause:** Unclosed or mismatched tag, unescaped '&' or '<' in a value, or a truncated transfer.
- **Fix:** Open the file at the reported line, fix the markup (escape & as &amp;) and resend.

### XML-002: Document fails XSD schema validation

- **Severity:** error
- **Why it matters:** Receivers validate against the official schema and reject documents that do not conform.
- **Likely cause:** Element in the wrong order, missing required element, or a value of the wrong type.
- **Fix:** Fix the element named in the message; validate locally against the same XSD before resending.
